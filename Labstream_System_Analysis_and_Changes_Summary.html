LABSTREAM: SYSTEM ANALYSIS & ENHANCEMENTS

Diagnostic Laboratory & Test Result Portal | ITP 108 Event-Driven Programming
Authors: Keegan P. Alviz, Raiven A. De Omania, Ian Keane R. Gregorio, Mark Joseph C. Navarro | Adviser: Prof. Jayson P. Joble
1. Executive Summary & Scope Realignment

The supplied proposal defines Labstream as a system for one diagnostic laboratory and excludes multi-branch management from the initial implementation. The current implementation is constrained to that baseline: one laboratory record per database, no branch entities, and no clinic-code prompt at sign-in. clinic_id remains an internal key for the single laboratory record.

  • Scope Decision: The canonical schema and API enforce one laboratory per database. Branch assignments and branch tables are removed. Existing databases must pass the guarded single-laboratory migration; it stops if it finds multiple labs or branch data requiring manual review.
  • Supported Result Modalities: Aligned with Proposal Limitation #4 (Text and numeric results with reference ranges). Complex antimicrobial susceptibility matrices and cytology narrative templates were deprioritized, focusing on scalar and panel laboratory testing.
  • Walk-In Cash Billing: Aligned with Proposal Limitation #5 & #6 (In-person cashier settlement). Third-party payment gateways and HMO claim workflows were excluded in accordance with the proposal.
  • Manual Encoding Model: Aligned with Proposal Limitation #3. Technologists encode values manually; hardware analyzer/LIS interfaces are omitted.
2. Deployed Environment Root Cause Analysis (Render)

A discrepancy was observed where the local development instance correctly retrieved and displayed staff accounts and catalog records, whereas the deployed Render production instance returned empty tables despite reporting a successful database connection.

  • Root Cause Diagnosis: Render hosts the frontend as a static site and the backend as a distinct web service on different subdomains. The session cookie was configured with SameSite=Lax, preventing browsers from transmitting the HttpOnly authentication cookie on cross-origin fetch requests (credentials: include).
  • Secondary Vulnerability: The requireSameOrigin middleware strictly inspects Origin headers. If FRONTEND_ORIGIN does not strictly match the static site domain, state-changing POST/PATCH requests were rejected with HTTP 403.
  • Implemented Resolution: Updated cookie options in backend/src/routes/auth.js: sameSite: process.env.NODE_ENV === "production" ? "none" : "lax" with secure: true. This allows modern browsers to safely attach the session cookie across domains.
3. Core Enhancements Implemented (Aligned to Proposal)
  • Admin Operational & Revenue Reports: Upgraded backend/src/routes/administrator.js to compute live Total Revenue (month-to-date) and Average Turnaround Time (TAT from payment to release). Integrated dynamic cards and tables into Reports.jsx and AdminDashboard.jsx, complete with Excel/CSV export and print stylesheets.
  • Patient Portal Result Report: The report includes patient identity, laboratory name, per-test results, units, saved reference-limit snapshots, abnormal flags, and pathologist interpretation. It uses neutral release wording and does not imply an electronic signature that the system does not record. Print styles support browser PDF export.
  • Multi-Analyte Diagnostic Panel Builder: Transformed the administrator test catalog form (TestCatalog.jsx) to support multi-parameter panels (e.g. Complete Blood Count indices, Urinalysis) with custom units, options, and validation. Added a "Params" inspector modal backed by a new endpoint: GET /api/admin/tests/:id/configuration.
  • Persistent Cashier Queue: Queue tickets and currently called requests are stored in the database. Authenticated call, call-next, and dismiss operations are audited and synchronized within the single laboratory.
  • Zero-Fee Waiver Processing: Zero-total requests use a distinct waiver payment method; positive settlements remain cash. The additive migration for existing databases is documented but has not been run against the user's Supabase database.
